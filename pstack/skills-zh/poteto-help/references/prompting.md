# 推敲提示词

提示词要说明意图与完成检查。步骤由手册提供，所以几句平实的话胜过一份规范。

## 要写进去

- 目标。说明哪里不对，或用户想要什么。
- 完成检查。它必须能通过或失败。"做得更好一点"和一个时长都不是检查。
- 要展示的证据。要求真实的命令输出、流程录像、存储的值，或前后对比的数字。
- 用户已知的信息。一个现象、一个复现步骤、一段日志或一个链接，能省掉智能体一次搜索。
- 真实的约束。"先复现"、"先不要改任何代码"、"行为零变化"、"在我复核之前不要继续"，每一条都会改变智能体的做法。

## 不要写进去

- 怎么做。说清要达成什么，给智能体留出找更好办法的空间。
- Skill 或步骤清单。手写的顺序会丢掉或打乱手册本会保留的步骤。只在要推翻某个选择时才点名某个 Skill。
- 用户对原因的猜测，除非智能体已经复述过问题。写出的猜测会收窄搜索范围。

## 先加载上下文

- 面对一份嘈杂的报告，先让智能体用自己的话、用平实的英语复述底层问题，再做其他事。误读会在任何代码出现之前暴露出来。
- 在新对话中，用 `/recall` 调取此前关于该主题的工作。旧对话里有新智能体所缺的上下文。
- 在改动不熟悉的代码之前，用 `/how` 了解机制、用 `/why` 了解原因。没有追踪过模型的智能体会在第一个看似合理的地方修症状。
- 让 `/teach` 为某个选择立论，例如"说服我它修的是成因而不是症状"。立论比摘要更容易核验。

## 先设计再规划

- 永远不要接受第一个设计。要求为几个选项做原型，界面类要附截图或视频，并依据证据来挑。
- 让原型回答悬而未决的问题。不要对抗式地评审一份抽象计划，因为评审者会凭空造出从未发生的风险。
- 对于共享包或 API，先要 README 或教程，再回溯到代码。文档会成为智能体自我核对的目标。
- 等设计定下来之后再要计划。计划的每一步都以一个检查收尾。

## 简短跟进

- 一旦对话已经承载了任务，"do it"、"continue"、"keep going until done" 就是完整的提示词。
- 主题变化时以"new task"开头。否则该模式会把这条消息当作下一步。

## 离开之前

- 说"im going to bed"或"im stepping away"，这样智能体就会停止提问。
- 把完成条件写成每轮迭代都能运行的检查，并把该判定条件交给 `/loop`。
- 要求从指定的基线开一个全新的工作树。
- 预先回答智能体本会停下来问的事，例如"提交前不用问我"。
- 要求留一份决策日志以便事后审计。
- 给出退出条件："如果你真的卡了几个小时，就停下来并写明原因"。

## 一行式引导

- 重述目标："i said the goal is to repro. i did not ask for a fix yet."
- 点名原则："apply prove it works. show me the real output, not the build log."
- 原则名之所以有效，是因为智能体已经读过那条规则。它的回复会点名该规则改变了哪个决定。
