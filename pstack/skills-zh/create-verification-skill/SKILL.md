# 创建验证技能

每个严肃的项目都需要一种脚本化的方式来驱动真实应用并证明其行为：启动它，像用户那样操作某个功能，并捕获证据。本技能会把这件事生成为项目本地的技能（Skill）（`.cursor/skills/verify-<app>/`），并针对该仓库量身定制。你写出的生成产物是给下一个智能体看的，而不是给人看的：它会在任务进行中被冷读，读者是一个从未见过这个应用的智能体。

## 1. 访谈仓库，而不是访谈用户

从代码库中回答下面这些问题，只向用户询问你无法观察到的事项：

- **界面形态（Surface）：** 用户实际接触到的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用，还是库？一个仓库可能同时有多种；选出主要的那个，并记录其余的。
- **运行（Run）：** 应用在本地如何启动？优先使用仓库自己文档化的开发命令（package scripts、Makefile、README 快速开始）。记录端口、环境变量、种子数据和鉴权。
- **驱动（Drive）：** 智能体如何以编程方式与之交互？先看现有测试装置——Playwright/Cypress 用例、expect 脚本、PTY 辅助工具、可用 curl 访问的端点、调试端口。只有在没有的情况下，才选择通用方案：Web 与 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY 装置，服务用纯 HTTP。
- **观察（Observe）：** 可以捕获哪些证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **隔离（Isolate）：** 两个实例能否并行运行（端口、数据目录、配置文件）？如果不能，就在生成的技能中说明这一点：拒绝重复驱动同一个共享实例，胜过破坏用户的会话。

如果这份检出原样无法构建或启动，先解决它（或精确地报告出来）再生成；针对一个坏掉的基础写出的技能只会教出错步骤。当某个无关的缺失资源挡住了启动（API 从不提供服务的静态目录、一个示例配置），生成的技能可以创建它，但要明确标注为验证脚手架，并在清理阶段删除。

## 2. 生成技能

写入 `.cursor/skills/verify-<app>/SKILL.md`，包含 YAML frontmatter（`name: verify-<app>`，以及一个 `description`，其中写明应用名、界面形态和何时该用它——没有 frontmatter 技能就不会被注册），并包含以下小节，每一节都要基于访谈的实际发现（不留占位符）：

- **启动（Launch）：** 用于验证的启动命令原文，以及如何判断它已就绪（一行日志、一个提示符）。启动必须能从空数据目录到达可用状态，包括任何迁移和种子数据。就绪意味着可用，而不只是某个进程有响应。数据库健康检查可能通过，而它的初始化脚本仍在运行。要包含拆除步骤。对于短命的 CLI 或 TUI，没有需要保活的服务器：启动意味着构建一次二进制（或安装依赖），然后让每次驱动在自己的隔离 PTY 或 tmux 会话中启动。
- **体检（Doctor）：** 一个只读检查，回答“这个实例值得驱动吗？”——进程存活、版本/构建正确、端口归我们所有、鉴权有效。只要有任何异常，智能体就应首先运行它。
- **驱动（Drive）：** 用本仓库真实的选择器/命令写出的装置方案，而不是示例。优先使用稳定的句柄（ARIA 标签、data 属性、提示符字符串、路由路径），而不是坐标和 Tab 顺序。
- **证据（Evidence）：** 为证明要捕获什么、存放在哪里。写明证明标准：走真实的用户路径，而不是内部 setter 或仅测试用的端点；同时捕获操作和操作后的状态，而不只是最终画面；在可见结果之外验证副作用（写入的文件、插入的行、发出的消息）；只有生产边界已经隔离了外部系统时才使用 mock。当安全路径是 dry-run 或测试模式时，要通过观察（文件、网络、git refs）来验证它实际跳过了什么，而不是相信它的名字：有些 dry-run 仍会访问网络或打开浏览器。
- **清理（Cleanup）：** 如何拆除本次运行创建的实例。绝不要按进程名杀进程；只杀你自己启动的。清理删除实例和临时状态，但绝不删除证据：证明产物要在拆除后存活，存放在技能指定的位置。
- **辅助脚本（Helpers）：** 技能附带的任何脚本都可执行，且其调用方式在技能正文中给出。需要读者反向工程才能用起来的辅助脚本，不算辅助脚本。

## 3. 播种功能地图

创建 `.cursor/skills/verify-<app>/features/README.md`，并为你能识别出的每个面向用户的功能各创建一个文件（先从路由、命令、菜单或文档中挑出最前面的 3-5 个开始）。遵循 [`references/feature-map-example/`](references/feature-map-example/) 中的形态，包含一个 README 索引和每个功能一个文件。每个文件都要从用户视角回答：这个功能是什么、如何到达、如何用装置驱动它、以及什么可观察的结束状态能证明它可用。四个 H2 分别是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺少某条用户旅程所需的前置条件，该旅程应报告失败，原因写进该功能的 `Gotchas`。绝不要为了让旅程通过而弱化它。功能地图是仓库持续维护的验证来源；当地图列出了多个入口点时，只驱动一个方便入口的证明是不完整的。

## 4. 交付前先证明生成的技能可用

按它自己的说明完整跑一遍：启动、体检、驱动一个已在地图中的功能（一个就够；地图存在的意义是后续运行覆盖其余部分）、捕获证据、清理。清理之后，确认证据仍存在于指定位置——把证明吃掉的清理会判定此步失败。修好失败之处，并且在每次失败的迭代后也运行生成的清理，这样中断的尝试不会遗留进程和端口。从未执行过的生成技能只是草稿，不是交付物。如果你是在真实目标的替身中完成证明（用容器代替全新虚拟机，用本地栈代替远程栈），列出替身做了而目标不会做的每一个准备步骤。在真实目标上跑一次覆盖它们之前，这些步骤仍属未验证。

## 5. 提供维护闭环

向用户指出 `/maintain-verification-skill`，用于在应用变化时保持地图诚实。只有当用户询问时才建议执行频率。
