# Notes 验证地图

本目录是验证 Notes 面向用户行为的维护来源。驱动应用之前先读索引，然后使用对应的功能文件作为操作方案。

## 基线前置条件

- 在 `http://127.0.0.1:4173` 启动 Notes，并使用一次性的数据目录。
- 设置 `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID`，以免并发运行共享状态。
- 播种标题为 `Quarterly plan` 和 `Grocery list` 的笔记。
- 把 `control-notes` 和 `notes` CLI 放入 `PATH`。
- 运行 `control-notes doctor`，并要求输出预期的 URL、数据目录和构建版本。
- 绝不要驱动不是由本次验证运行启动的实例。

## 驱动约定

- 除非其前置条件另有说明，每条操作方案都从基线状态开始。
- 优先使用 ARIA 角色和可访问名称，而不是 CSS 选择器或 DOM 位置。
- 把每条命令都当作字面内容。引号内的名称和参数保持不变。
- 浏览器操作通过 `control-notes browser` 执行。
- 终端操作通过 `control-notes cli -- <command>` 执行。
- 变更操作之后恢复播种数据。清理时不要删除证明产物。

## 证明与跳过报告

- 捕获用户操作和操作后的状态，而不只是最终画面。
- UI 证明包含 ARIA 快照和一张能看到应用标识的截图。
- CLI 证明包含命令、stdout、stderr 和退出码。
- 变更证明包含对已存储值的第二次只读查看。
- 每件产物都要记录所使用的功能 ID 和入口点。
- 报告不可达路径时，要给出尝试的命令和未满足的前置条件。
- 不要把通过其他路径跳过的入口点报告为已验证。

## 功能文件约定

每个功能文件以一个 H1 标题开头，并用一段话描述用户可见的行为。然后按此顺序使用恰好四个 H2 小节。

1. `Sub-features` 列出简短的 ID，每个行为一行。
2. `How to get to it (user POV)` 列出每个用户入口点。
3. `Driving it with <harness>` 以 `Preconditions:` 开头，并使用带标签的列表项，把每个用户操作与确切的命令和可观察结果配对。
4. `Gotchas` 列出可能浪费或使验证运行失效的陷阱。

把实现细节排除在地图之外。只写用户路径、稳定句柄、必需状态、命令和可观察证明。

## 功能

- [创建笔记](./create-note.md) 覆盖浏览器与 CLI 的创建、取消、持久化和清理。
- [搜索笔记](./search.md) 覆盖工具栏、键盘和 CLI 搜索，包括命中、空态和清除状态。
