# 影响半径

在变更上线之前，找出它在别处破坏什么。用于"X 的影响半径"、"这可能破坏什么"，或评审一个你还不信任的小 diff。

`how` 和 `why` 的配套技能。`how` 告诉你代码做什么。`why` 告诉你它为什么长成这样。影响半径告诉你它在别处破坏什么。

列出调用者不是这份工作。智能体一秒就能 grep 出这些。这份工作是 grep 显示不出来的破坏。

## 不要相信你自己写的报告

一份读起来对的影响半径报告毫无价值。无论真假，它读起来都很有说服力。所以不要把报告交回去。找出整件事所依赖的一两个事实，并通过运行代码证明它们。

### 你有多确定

对变更安全性所依赖的每个事实，尽可能廉价地把它推到下面清单的越靠下越好，并说明它停在哪一步。

1. 你只是这么说了。单独看毫无价值。
2. 你指向了那一行。一个真实的 `file:line`，或库自身的源码。
3. 你证明坏情况不会发生。你一步步走完失败路径，它走不到。
4. 你运行了它。一个脚本或测试，调用真实代码，如果你错了就大声失败。
5. 你在运行中的应用里复现了它。

第 4 步通常是一个小脚本，它导入应用实际发布的同一个库，并调用你担心的那个确切函数。

## 步骤

1. 读变更。diff、它新增、修改和删除的符号，以及它现在行为有何不同，包括 diff 没有明说的部分。拉取 PR 及其提交。
2. 找出它之所以安全所依据的那一个事实。大多数看起来有风险的变更之所以安全，是因为某个单一事实，比如"这个调用只会丢弃已经失效的缓存条目，别的什么都不做"。找到那个事实。如果它成立，大多数风险情形一次性排除。把时间花在这里，而不是一长串可能项。
3. 看 grep 停在哪里。读你所调用库的源码，检查它锁定的版本和任何本地补丁。弄清东西何时运行：微任务、卸载与拆卸、Solid 与 React 的差异。跟进符号搜索会漏掉的东西：API 返回的 JSON、一个数据库列、一种线上格式、另一种语言读取同样的字节、一个功能开关、三跳之后的代码。
4. 对每个风险保持诚实。给它真实的概率和真实的代价。保留你已确认的风险。把你检查过并排除的风险单独列出。引用真实的 `file:line`，搜索一无所获也是答案，绝不要编造调用者或 API。
5. 证明那一个事实。写一个运行真实代码的脚本或测试，运行它，粘贴结果。
6. 对于大范围或广域变更，把它当作 `arena` 来跑。让多个模型回答同一个问题并合并答案。不同模型会抓到不同的真实缺陷。

## 交回什么

- **它做什么。** 改了什么，包括不明显的部分。
- **它之所以安全所依据的那一个事实。** 陈述它，说明你把它推到了第几步，并给出证明。如果证明不了，写"未证明"。
- **风险。** 每条说明它如何破坏、`file:line`、可能性与严重程度、以及如何检查。对重要的几条粘贴证明。
- **已排除。** 你检查了什么，以及为什么没问题。
- **合并之前。** 能抓住真实缺陷的最便宜测试或复现，包括你写的脚本。

通过 `unslop` 来写，引用真实代码，在发往任何公开场合之前删掉一切私密内容。

**回复：** 上述报告，其中那一个安全事实要么已证明，要么标记为未证明。
