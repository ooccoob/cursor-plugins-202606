# 状态图

这张图用阅读它的人自己的语言，展示系统如何在状态之间迁移。这个人，也就是读者，判断行为是否正确。

## 运行

在仓库之外的临时目录中工作。写一份 TLA+ 规范及其配置。然后运行：

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` 是 TypeScript 文件，因此要用能执行 TypeScript 的运行时来运行它。`scripts/statechart` 是一个 POSIX shell 脚本，负责挑选其中之一。在原生 Windows 上，用 Node 22.18 至 22.x，或 Node 23.6 及更高版本，运行 `node --disable-warning=ExperimentalWarning <skill dir>/scripts/statechart.ts`。

首次运行会用 mise 安装 TLC 和 Java，需要网络。

## 编写规范

- 把读者认可的每条规则写成 INVARIANT。规则可以关于某个界面、某个结果、某个已存储的值或某条消息。如果模型中没有对应某条规则的变量，就加上这个变量。绝不要为了让规则成立而弱化它。
- 把 `Next` 写成各动作的析取，例如 `YouPressPlay \/ YouPressStop`。如果不这样做，TLC 会把每一步都命名为 `Next`。
- 没有出边的状态会破坏 `NoDeadlock`，即使它是正确的终止状态也一样。当 INVARIANT 或 PROPERTY 已经使用了这个名称时，规则为 `CHECK_DEADLOCK`。在 `Next` 中加入一个只在终止状态为真且不改变任何东西的动作，例如 `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars`，并在 `step()` 中给它一个标签。

## 选择图表

需要判断的工作由你来做：每个状态和箭头上的文字、阶段及其颜色、标题，以及给读者的报告。把你的工作放进一个 view 模块，并用 `--view` 提供它。

为了展示读者的语言，view 导出 `state(vars)`。`state()` 返回的值决定形式：

- 字符串给出扁平图：`export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 数组给出父状态：`export const state = (v) => v.main.split(".");`
- 对象为每个键给出一个并行区域：`export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

用读者能看到或关心的内容给每个状态打标签，例如 "Paying" 或 "Lease held, write pending"。标签中不要出现变量名。在 `vars` 中，TLA+ 序列是以 1 为起始键的对象，所以 `v.pc[1]` 就是 `pc[1]`。集合是数组。

view 还可以导出 `step(action, from, to)`。它接收 TLC 动作名以及该步之前和之后的值，返回箭头的标签。按用户看到的方式写每个步骤标签，例如 "you press play" 或 "the connect fails"。不要写代码名或 TLA+ 动作名。在图中终点相同的两个动作会得到相同标签，从而共用一条箭头。

当某一步只在某些条件下发生时，在标签末尾用方括号写出该条件，使用读者的语言，例如 `you press play [while the file loads]`。在区域图中，命令会用其他区域标签的语言，把该条件写在箭头上的那些区域处，例如 `[when Offline]`。你写的方括号会替换它，于是从同一个状态出发的两条箭头可能看起来一样。因此在区域图中，不要为另一个区域上的条件写方括号。当某个没有任何标签体现的值决定某一步的走向时，在标签中写出结果，例如 "the roster read fails"。

view 还可以导出以下内容：

- `group(vars)` 返回阶段名。每个图状态获得其所属阶段的颜色。当某个图状态背后的模型状态属于不同阶段时，该状态没有颜色。
- `colors` 为每个阶段名指定一个颜色类。
- `title` 是一个字符串，图会把它显示在顶部。

命令对每个模型状态最多调用一次 `state()` 和 `group()`，对每一步最多调用一次 `step()`。图和报告都使用这些答案。因此让每个函数只依赖它的参数。

图不绘制停留在一个标签内的步骤。当读者必须看到这样的步骤时，拆分标签。

目标是约 20 条箭头或更少，因为更密集的图难以阅读。先让 `state()` 返回更粗的标签。把行为相同的值合并为一个标签，省略读者不需要的细节，例如一个在途调用，而它的返回不改变任何东西。保留 bug 路径上的每个状态，保留每个标记。把 `breaks` 状态合并为 `mayBreak` 会掩盖规则在哪里被破坏。不要合并破坏不同规则的两个状态，否则读者看不出哪条规则在哪里被破坏。如果图仍然太密，对读者不需要的步骤从 `step()` 返回 `null`，例如每个状态都有的重置，或者箭头只是重复其他箭头的步骤。隐藏步骤时遵守这些规则：

- 保证每个图状态都能通过箭头从某个起始状态到达。
- 对每个在模型中有出边的图状态，至少保留一条出边箭头。
- 要么隐藏一条箭头的所有步骤，要么一个都不隐藏。只隐藏其中一部分时，它的条件会变窄。
- 在交接说明中写明图隐藏了哪些步骤。

## 阅读报告

- 在图中，破坏规则的状态带有 `breaks` 类。当它背后只有部分模型状态破坏该规则时，它带有 `mayBreak` 类。图例给出每个标记对应的规则。当两条规则同时被破坏时，它在一个标记上同时写出两者，因此在交接说明中要写明哪个状态破坏哪条规则。在区域图中，当包含某状态的所有区域状态组合都可能破坏某条规则时，该状态获得标记。当某个组合可能破坏规则而其中没有任何状态带标记时，该组合中的每个状态都获得标记。
- TLC 会越过破坏规则的状态，所以图会显示 bug 之后的状态。
- 由于 TLC 会越过 bug，没有状态上限的模型可能无休止地运行。把常量取小，或加一个 CONSTRAINT。
- 使用 VIEW 或 SYMMETRY 时，TLC 把视为相同的状态计为一个状态，图也只画这一个状态。箭头可能指向它，而不是该步实际到达的状态，报告会说明这一点。
- TLC 会在 CONSTRAINT 或 ACTION_CONSTRAINT 之后的每个状态中检查规则，但不会探索该状态，也不会对它做死锁检查。当 TLC 为某条规则找到的最短路径终止于这样一个状态时，图会画出该状态，报告会给出这条路径。图不绘制该边界之后的其他状态。这样一个状态中的死锁不会显示。TLC 也会在 ACTION_CONSTRAINT 排除的每一步之后检查规则，即使它以另一种方式到达下一个状态。当 TLC 为某条规则找到的最短路径以这样一步结尾时，图会画出这一步。
- 命令按原样配置用一个 worker 通过 TLC 检查规则。当某条规则被破坏时，命令移除该规则并再次运行 TLC，直到没有规则被破坏。首次破坏之后，每次运行在 100,000 个不同状态处停止，以免大型模型无休止地运行。当某次运行达到该上限或因错误停止时，报告会在 "Rules not checked" 下列出它未检查的规则，图不会标记它们。未检查的规则可能成立也可能被破坏。要检查它，从配置中移除被破坏的规则，或让模型变小。该上限会加入一个改变 TLC 变量顺序的模块，因此对某个性质，TLC 可能找到与不加该上限的运行不同的反例。
- `tlc.out` 是 TLC 按原样配置打印的内容。当图没有显示某条被破坏规则的 bug 路径时，`tlc-RULE.out` 是 TLC 在找到该 bug 的那次运行中打印的内容。当 TLC 重复它的第一条警告时，普通 TLC 会打印两次，但 `tlc.out` 只显示一次，因为 TLC 在命令读取的输出中省略了第二份副本。这仅在 Java 以 `-XX:+UseParallelGC` 运行时发生，否则 TLC 的第一条警告就是它建议传入该标志的提示，而这条提示只打印一次。

## 展示图表

把 `chart.mmd` 作为 `mermaid` 代码块展示给用户。图的状态预算为 500，按原样配置由 TLC 统计。超过该上限时，图只绘制通往被破坏规则的路径；当没有规则被破坏时，命令不写 `chart.mmd`。它仍会检查每条规则，报告会给出状态数和每条 bug 路径。要看到整张图，把模型变小。

用 Pele 渲染图表。当用户要求图片，或图大到无法作为文本阅读时，遵循 `references/render.md`。除非用户要求，不要使用其他渲染器。

## 交接

把每张图及其 Mermaid 文本交给必须做决定的人。为每个 bug 加一行：规则、读者对该规则的那句话，以及按报告编号给出的路径。说明模型省略了什么。给出重新生成这些文件的命令，并配一个新的 `--out` 目录。

当模型描述的是代码时，把每条 bug 路径对照真实代码回放，作为测试或现场复现，每个动作一步。如果 bug 没有出现，先认为模型是错的，直到你证明它不是。
