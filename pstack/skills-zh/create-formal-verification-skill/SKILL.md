# 创建形式化验证技能

测试检查的是有人想到要写的那些用例。形式化验证检查一个声明范围内的所有用例：模型中步骤的每一种顺序、有界范围内的每一个输入，或每一个输入。本技能找到仓库中最需要这一点的部分，验证它的某一个性质，并留下一个项目本地的技能，让下一个智能体能对照该性质检查变更。要写给一个冷读、在变更过程中、从未见过你工作的智能体。用户必须能够信任结果，并在不学习验证语言的前提下据此行动。

## 从代码中选择目标

从代码库中回答，只向用户询问你无法观察到的事项。如果用户指定了某个区域或某个缺陷，就从那里开始。

好的目标是代码做出的一项承诺，其破裂会伤害用户，而测试很少覆盖到使其破裂的那个用例。选择仓库中最强的这类目标，而不是最容易验证的那个。

## 让问题选择工具

选择以最低成本回答该问题的工具：模型检查器、证明助手、基于 SMT 的验证器，或其他工具。事件是否可能以糟糕的顺序发生，通常适合用模型检查器对设计的小模型来验证，TLA+ 是任何语言中此场景的默认选择。代码本身对每个输入是否都表现正确，例如内存安全、溢出或数据结构不变式，通常适合用直接作用于代码的验证器。如果没有任何验证器能作用于这门语言，就明确说明，并用生成的输入测试真实代码，而不是函数的手工模型。某个性质必须在任意规模下成立、有界不够时，可能需要一个证明。优先选择仓库开发者能安装并运行的工具，并告诉用户你为什么选它。

## 什么算好

- **忠于代码。** 模型或证明的每一部分都指向评审者能打开的代码。验证视为不可分割的一步，在代码中也就是不可分割的一步。命名来自本仓库。
- **能够失败。** 你从未见过失败的检查证明不了任何东西。要在它所守护的代码的破损变体上展示每个性质的失败，例如移除某项检查或重排某个步骤。
- **发现就是发现。** 当当前代码违反了该性质时，用代码的语言连同反例一起报告。不要为了让其通过而弱化性质或模型，也不要改动产品代码，除非用户要求。
- **对范围诚实。** 说明验证了什么、在哪些边界和假设之下、以及排除了什么。通过只覆盖模型或边界，不覆盖整个系统。
- **不借助工具也能读懂。** 用各一句平实的话陈述该性质和危害。用代码的语言把反例讲成一段简短的步骤序列。
- **重跑成本低。** 一条命令、一个可复现的工具版本、一次足够短的运行，让下一个智能体愿意在每次相关变更上都用它。
- **与代码同步。** 记录每项检查覆盖哪些文件和函数，以及你最后一次确认该验证确实描述它们的提交。当被覆盖的代码在该提交之后发生变化时，下一个智能体应能看出该验证需要再看一眼。

## 生成验证技能

写一个带 frontmatter 的项目本地技能，命名该区域并说明何时使用。没有 frontmatter，技能就不会被注册。仅凭该技能，下一个智能体必须能够判断某次变更是否触及被验证的代码、运行检查、区分真实缺陷与建模错误，并在变更是有意的时候更新验证。把覆盖记录和同步提交写进技能，并告知下一个智能体：只有在确认验证描述了新提交处的代码之后，才能把同步提交前移。使用本仓库真实的命令、路径和名词，不留任何占位符。

如果检查是一个 TLA+ 模型，告知下一个智能体用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能读取每个结果。它把检查器发现的每一处不变式违反，以其最短路径用平实的语言展示出来。当检查通过时，`/statechart` 会画出系统在状态间如何迁移的图表。要以名称引用 `/statechart`。它的命令、选项和文件路径会随版本和机器而变化，因此不要把其中任何一项复制进生成的技能或其脚本。

## 交付前先证明它可用

像下一个智能体那样，在一个会破坏真实代码中该性质的临时变更上，完整遵循一遍生成的技能。它必须捕获该破坏。然后撤掉临时变更，确认检查回到起始状态：通过，或仅在你将要报告的发现上失败。从未运行过的验证技能只是草稿。如果技能漏掉了该破坏，或某个步骤无法运行，就修技能或修验证，而不是修临时变更。

## 交付

告诉用户你验证了什么、用了哪个工具及原因、边界是什么、检查用平实的话发现了什么、如何运行、以及它不覆盖什么。只有当你发现了相近的目标时才建议第二个目标。向用户指出 `/maintain-formal-verification-skill`，用于在未重新检查的变更之后把验证重新对齐。
