# 想清楚并落地（Figure it out）

当任务不匹配任何 playbook 时，就自己设计一个。在任何代码之前，交付物就是工作流本身：一系列阶段，按任务规模调整严谨程度，运行科学方法，并留下人可以离开后回来审计的决策轨迹。

## 开始

打开一个待办清单，第一项是阅读 **poteto-mode** 技能的 Principles 章节。然后把下面的阶段作为待办项加入。

## 阶段 A：框定

先落地，再承诺。在你能够陈述以下内容之前，不要开始执行：

- 完成定义，写成一个可证伪的谓词（**prove-it-works** 原则技能）。
- 范围，量化：粗略的单位与工作量，加上落地勘察暴露出的阻塞项。
- 严谨等级，偏向高。单向门和高影响半径的取更多。可逆的低风险步骤取更少。严谨是关卡和产物，不是"再努力一点"。

在承诺长时间执行之前，先呈现框定与取舍。可逆的工作直接推进（**never-block-on-the-human** 原则技能），但数小时的执行值得一次检查点。

## 阶段 B：设计工作流

分解为原子的、可独立落地的单元。按最大未知优先排序。脚手架和验证先于功能（**foundational-thinking** 原则技能）。

- 在工作之前构建验证装置，并从变更前状态捕获基线，这样检查读起来就是"旧值 vs 新值"。
- 对单向门的设计决策，运行 **architect** 技能（它会运行 **arena**）。对形态已经具体的机械性工作跳过它。对已定设计再跑一次 arena 属于过度工程（**laziness-protocol** 原则技能）。
- 决定哪些工作扇出。只在接缝处并行，并给每个工作者自己的工作树或分支（**separate-before-serializing-shared-state** 原则技能）。不要过度扇出。按 **poteto-mode** 技能的 Subagents 章节，为每个子代理挑选适合该任务的推理等级。
- 把设计好的阶段清单写下来。那份清单就是人复核的对象。

然后执行该设计。把它的步骤作为具体条目加入待办清单，位置在阶段 C 与阶段 D 条目之间。在阶段 C 的循环纪律下运行每一步，并把阶段 D 的日志贯穿其中，每落地一步就加一行，而不是把整条轨迹留到最后。

## 阶段 C：运行循环

每个单元都是一个实验。陈述假设，做最小改动，在真实产物上对照谓词测量，有进展就保留，没有就回滚。应用 **sequence-verifiable-units** 原则技能，在开始下一个单元之前验证当前单元，而不是把检查攒到最后。

- 通过检查产物来验证，绝不相信自我汇报。当某件事通过得太容易时，先怀疑观察方法，再怀疑系统。
- 为委派的工作配一个裁判。如果工作者钻了关卡的空子，重置并加固契约。如果关卡本身错了，在它自己的变更里修关卡，而不是绕开它。
- 判定结果是 VERIFIED、NOT VERIFIED 或 INCONCLUSIVE。Inconclusive 不是通过。不要隐藏负面结果。

## 阶段 D：保留审计轨迹

通过 **show-me-your-work** 技能记录这次执行。figure-it-out 的工作通常足够宏大，值得把轨迹提交，让复核者能在 PR 里读到它。轨迹加上 diff，才能让人回来并信任这项工作。

## 阶段 E：验证并交回

在真实产品上、而不只是在验证装置上，用阶段 A 的谓词检查整体。把任何反复出现的纠正固化为关卡、lint 规则、检查或脚本（**encode-lessons-in-structure** 原则技能）。

**回复：** 你设计的 playbook、严谨等级及其理由、决策轨迹路径、哪些已按谓词验证、哪些仍然开放。
