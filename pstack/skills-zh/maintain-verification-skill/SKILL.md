# 维护验证技能

应用一变，功能地图就开始腐烂。本技能是由 `/create-verification-skill` 生成的技能（或任何带功能地图的项目本地验证技能）的维护闭环。严谨性的单位是功能，而不是每一句话：从源码覆盖每个功能文件并实际驱动每个功能，而不必逐条验证每个列表项。

## 结果

选择其中一种，并说明是哪种：

- **clean** —— 每个功能都获得了源码覆盖和实际覆盖；没有值得交付的内容。不建分支，不提 PR。
- **changed** —— 提交一个 PR，交付已验证的文档、装置或地图修正。
- **blocked** —— 覆盖无法完成，或某个已验证的修复无法安全交付。要明确说明是什么阻塞了它。

## 编辑范围

只编辑验证技能自己的目录（其 SKILL.md、features/ 以及它拥有的任何装置脚本）。运行期间绝不编辑产品代码：地图描述而应用已不再做的行为，要么是文档漂移（修正地图），要么是产品回归（报告它，不要在文档里粉饰它）。

## 执行流程

0. **定位目标。** 找到要维护的验证技能：正文包含启动/驱动小节和功能地图的项目本地技能（通常是 `.cursor/skills/verify-*/`）。有多个候选就询问是哪一个；一个都没有就停下来，指向 `/create-verification-skill`，而不是凭空发明一个目标。

1. **索引卫生。** 读取功能地图的 README，并用 glob 列出其同级文件。修正缺失、多余、重复或失效的条目。这一步很轻量，不生成清单。

2. **源码波次。** 每个功能文件一个只读子代理，并发启动。每个子代理从源码解释“这个面向用户的功能是如何工作的？”，标出可能的文档漂移并给出引用，并返回一份简明的实际验证方案。子代理绝不驱动应用，也绝不编辑文件。返回结构：功能摘要 / 源码入口点 / 可能的漂移或无 / 一份方案。

3. **对齐。** 每个功能文件都有返回的摘要。把重叠的方案合并成尽量少的应用状态。抽查被引用的漂移；不要重新证明干净的说法。扫一遍最近的变更，找出地图中缺失的面向用户界面——在判定某项缺失之前，必须给出具体的源码路径。

4. **实际验证。** 即使源码看起来干净也必做。协调者负责全部驱动；遵循验证技能自己的启动模型——服务器和 UI 用一个长期存活的实例串行驱动，短命 CLI 则每次驱动用一个全新的隔离会话（由该技能的启动小节决定，而不是本节）。每个功能至少演练一次，并在整个验证过程中坚持三条不变式，无论出现什么失败：(1) 绝不要驱动一个自它上次出现异常行为后你还没做过健康检查的实例——首次驱动前体检，在会话为单位的场景下每个新会话都体检，任何失败的驱动之后再次体检，而在体检看不到的失败处（进程健康但 UI 卡死），重置到已知状态或重启，而不是指望它自己好；(2) 迄今捕获的证据必须在每次清理后存活，并在其指定位置核验，而不是假定；(3) 驱动启动的任何东西不得超出该次驱动的有用期限——失败迭代的残留必须清理，无论会话是卡住、已退出还是共享的（对共享实例，清理残留，而不是清理实例）。由技能漂移引起的体检失败属于漂移：在编辑范围内修好并重试一次——只重启修复所影响的部分，不多做——然后再判定本次验证为 `blocked`。无法到达的功能，只有在给出具体前置条件（鉴权、授权、操作系统、外部状态）和尝试过的路由时，才标记为 `verified-unreachable`；如果地图漏掉了这个前置条件，那就是漂移。分诊得出的任何装置修复，在交付前都要重新实际驱动一遍。最终拆除在本次运行最后一次驱动之后进行——包括那些重新证明——这样没有任何东西超出本次运行（按技能规定，证据保留）。

5. **分诊。** 用户视角描述错误或缺失 → 文档漂移，修正它。行为正常但装置无法驱动 → 装置缺口，修好它；装置修复遵循与生成时相同的辅助脚本规则（脚本可执行，调用方式记录在技能正文中）。应用行为确实坏了 → 产品缺口；记录给用户，不要放进这个 PR。

6. **交付或停止。** 对 changed：提交一个只含已验证修正的 PR，提交前先重读每个被改动的文件。对 clean 或 blocked：不提 PR，如实报告结果和覆盖情况。

在草稿位置保留简明的运行笔记（覆盖的功能、不可达的前置条件、确认的漂移、结果）；不要提交它们。
