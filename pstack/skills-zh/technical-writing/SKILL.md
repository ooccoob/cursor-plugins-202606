# 技术写作

写到疲惫的工程师第一遍就能读懂。

- 删掉每个不起作用的词。
- 用简短、日常的词："use"，而不是 "utilize"。
- 当某条规则让句子变差时，换一种方式改句子，或者就别动它。
- 写真实的符号、文件、标志或命令名，不要写它的同义词或对它的描述。
- 不要生造术语。用开发者会说出声的词。某个有名字的模式首次出现时，说明它的含义。

## 变化节奏

- 混合句子长度。拆开承载两个想法的句子。保留承载一个想法的长句。
- 解释里要有观点。参考部分保持干枯。
- 要具体。不是"schema 变更可能引发问题"，而是"重命名一列会让构建失败"。

## 先选模式（Diátaxis）

一份文档，一个模式。不要混用模式。拆分并链接。

- **教程：边做边学。** 说明学习者会构建什么。每一步都产出可见结果，并说明他们应该看到什么。解释只给一个从句加一个链接。
- **操作指南：通往目标的步骤。** 解决读者的问题。假定对方有能力。只写动作。允许分叉。用任务给指南命名。
- **参考：供查阅的事实。** 只做描述。干枯、完整、确定。镜像被描述之物的结构。
- **解释：理解与原因。** 一个有边界的话题。给出上下文：设计决策、历史、约束、备选方案。只有这里允许出现观点，其他任何地方都不行。

## 面向读者写句子（Google 开发者风格）

- 用"你"称呼读者，用现在时。
- 说清谁做什么。只有当施动者未知或不重要时才用被动。
- 把指令写成命令。把条件放在指令之前，把常见情况放在前面。
- 不用流行词，不用比喻性语言，不写"please"，在操作步骤里绝不用"simply"、"easy" 或 "quickly"。
- 不要预告，也不要用同一个短语开头连续的句子。
- 链接文字要说明链接指向哪里。
- 标题承载要点，用句首大写。每页一个 h1，不跳级。
- 序列用编号列表，其余用项目符号。用完整句子引出列表。保持条目结构平行。
- 代码用代码字体。UI 元素用粗体。使用连续逗号。删掉 "etc."。

## 让陈述一次只承载一个意思（STE 规则）

- 一句一条指令。其他地方的句子一句一个想法。
- 拆开超过约 20 词的指令，以及超过约 25 词的其他句子。
- 把警告或条件放在它所守护的步骤之前。
- 保留 "the" 和 "a"。
- 给每个词一个含义，每个动作只用一个词。
- 把流程写成直接命令，绝不写成叙述，绝不用被动。
- 尽量避开 "-ing" 形式的词。

## 不留下可作两种解读的句子（Global English）

- 把 "only" 和 "not" 这类词放在它们修饰的词旁边。
- 拆开过长的名词串。
- 让每个 "it"、"they" 和 "this" 都指向一个明确的对象。绝不用 "this" 或 "which" 指向整个从句。
- 不要省略动词，也不要省略标示结构的小词，比如 "that"。
- 在能防止误读时，在并列结构中重复冠词。说明 "and" 或 "or" 连接的是哪些部分。
- 用句号，不用分号或破折号。不用斜杠，不用 "(s)"。让括号里的内容成为完整的语法单位。
- 每样东西在每处都用一个名字。
- 跳过习语、口语表达、拉丁缩写和隐喻。

## 语气与仓库特定要求

- 对本技能涉及的每份文档应用 **unslop** 技能。该技能掌管注水模式目录：AI 词汇、填充语、模糊措辞、格式破绽。
- PR 描述和提交信息也是写作。除 Diátaxis 之外的每一层都适用于它们。PR 正文是一份让复核者一分钟内读完的简报。不要粘贴集群日志、SHA 列表或指标表格。用链接指向它们。
- 产品 UI 文案不是文档。这些用你产品的文案指南。
- 代码片段用制表符缩进。写真实路径。每个计数或目录树断言在落地它的那个提交上都必须为真，并附上可重新生成它的命令。
