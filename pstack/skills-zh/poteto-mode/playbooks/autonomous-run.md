### 自主运行

**你负责退出条件。先定义完成，然后不停顿地推进到完成。**

1. 在第一次迭代之前，把退出条件写成一个可检查的谓词（测试全绿、复现已修复、全部 N 个 PR 已合并、像素差异为零）。
2. 用 Cursor 的 `/loop` 命令（内置能力，不是 pstack skill）选择唤醒机制。要盯的事件（CI、某次合并、某个 ref 前进）交给一个监视子代理，由它在事件发生时唤醒你，并以较长的基于时间的脉搏作为兜底。没有事件时，用固定间隔的脉搏，间隔按"何时值得重新检查结果"来定。按 Subagents 一节，为每项工作挑选子代理的推理等级。
3. 每次迭代只做证据支持的最小改动，用谓词验证它，有进展就提交，没帮助的改动丢弃。所谓"可能有帮助"的双保险一律回滚，不能留着凑数。
   用 **sequence-verifiable-units** 原则 skill 编排工作顺序，每个单元验证通过再进入下一个，不要把检查都堆到最后。
4. 运行过程中发现的、有助于目标的问题归你处理。损坏的 skill、相关 bug、不稳定的验证器、评审噪音、工具故障、被遗漏的后续事项，以及可修复的漂移，都通过 poteto-mode 自行处理。计划外的修复单独开 PR。不要为可逆的工作停下来等人，也不要用 `AskQuestion`。只上报不可逆的操作、任何实验都无法定论的真实产品或偏好抉择，或者真正的死胡同。把谓词作为主线，每处理完一个附带修复就回到主线。
5. 每次迭代都按 **show-me-your-work** skill 做检查点，用一行记录改了什么、谓词是否推进。
6. 谓词满足就停止。进入平台期不是停止的理由，要继续推进并改变方法突破它。真正的死胡同要上报，而不是空转，也绝不能为了宣布胜利而放宽谓词。

**回复：** 退出条件、迭代次数、落地的内容、被丢弃的内容、最终的谓词状态。
