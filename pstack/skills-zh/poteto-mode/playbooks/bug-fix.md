### 缺陷修复

**你负责这个任务。规划、评审、验证。** 把排查和修复委派给子代理，自己留在主导位置。按 Subagents 一节，为每项工作挑选子代理的推理等级。

要讲科学。每一行交付的代码都能追溯到运行时证据。所谓"可能有帮助"的双保险只是假设，不是修复，不能交付。当证据推翻了某个假设，就回滚由它引发的改动。只交付证据支持的最小改动，别的一概不要。

1. 自己在匹配的界面上通过控制 skill（见 Non-negotiables）复现，即使某个调试或插桩协议让你请用户来复现。只有在给出明确、具体的理由说明控制界面无法触达目标时，才去问用户，而且必须先把该界面推到极限。如果无法直接复现，就合成触发条件、收紧条件，或加插桩直到它触发。
2. 用二分法定位原因。先形成候选假设，再逐个排除直到只剩一个。用受影响子系统的轨迹和 **why** skill 的回归历史来播种假设。每一轮都选能砍掉最多剩余问题空间的切分，取运行时证据，排除。当程序状态不清楚时，加插桩或日志，并在代码运行时读它。不要猜。长跑或顽固的排查用 Cursor 的 `/loop` 命令推进。在第 3 步的 `architect` 或 `interrogate` 铺开之前，先用运行时证据确认存活下来的*机制*。
3. 规划修复。如果它跨越函数边界，先 `architect`。用你配置的缺陷修复模型（默认 `claude-opus-5-5-xhigh-fast`）把实现委派给子代理，并给出具体范围。
4. 在同一界面上验证。原来的复现现在通过。"不确定"或界面不对都不算通过，要标出来。单元测试展示的是分支行为，不是缺陷不存在。
5. 安排提交顺序，让失败的复现在 git 历史里先于修复落地。当缺陷有廉价的本地测试路径时，按 **tdd** skill 的失败测试优先节奏执行。测试昂贵、偏集成或不清晰时跳过。
   这是 **sequence-verifiable-units** 原则 skill 的典范用法：先失败的测试，再叠上修复。
6. 运行 **Opening a PR** 手册。

**回复：** 哪里坏了、根因、修复、如何验证。逐字粘贴从失败到通过的复现输出。
