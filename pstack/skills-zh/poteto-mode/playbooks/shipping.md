### 交付（Shipping）

**落地什么由你负责。逐个独立验证每个 PR，只从根部落地已通过验证的那段连续栈，然后不要再去动这个栈。**

1. **先确定用哪个代码托管 CLI，再在每个 PR 落地前独立验证它。** GitHub CLI（`gh`）是默认选择。如果 `command -v origin` 成功且 Origin 能解析出仓库，则所有 PR 操作都用 `origin pr`。否则留在 `gh` 上并记录这次回退。绝不要求 Graphite（`gt`）。每个 PR 一个验证者，各自是一个 Cursor 云智能体，用相应的控制 Skill（例如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）像用户那样跑这处改动，父提交对照头提交，并在该 PR 上给出 `PASS`、`PASS+NOTES` 或 `FAIL`。只有来自未写这段代码的智能体的判定才算数，因为作者检查的是自己本想实现的东西。CI 全绿和机器人评审通过都不是判定，因为两者都不会像用户那样跑这处改动。
2. **只落地以最底部为根的那段连续已验证栈。** 从最低的未合并 PR 往上走，停在第一个没有 `PASS` 或 `PASS+NOTES` 的 PR 上。它下面的那些 PR 就是这段栈，最上面那个是天花板。某个已验证的 PR 若位于一个未验证 PR 之上，就要等，因为没有下面的代码它无法落地。如果某个 PR 的分支既不包含也不需要那段代码，它可以移到主干上单独落地。但它需要先拿到新的判定，因为它的旧判定是在那段代码垫底的情况下跑出来的，而主干上没有那段代码。
3. **复查判定是否仍然描述着当前代码。** 一个判定覆盖的是一个补丁，而链条变基会把其上方每个 PR 都移到新的 SHA 上，却不触发任何检查失败。在信任一个较旧的判定之前，把判定时的 SHA 与当前头提交做 `git patch-id` 对比。当补丁之间的差异只在测试、文档或 lint 配置上时，某条车道的结论仍然成立——前提是它跑的东西在两个 SHA 上构建结果相同（噪声除外）。噪声是指在判定 SHA 的两次构建之间同样会出现的差异，或是一个内嵌的提交 SHA。每一类噪声都要连同涉及的文件一并报告，让读者能自行核对该判断。改动本身仍然要跑新检查并过评审，因为旧判定从未见过它。没有构建产物的车道（例如开发服务器）无法展示这一点，所以要重跑它，并重新验证其他任何发生漂移的东西。
4. **自下而上落地，一次一个 PR。** 永远合并这段栈里最低的未合并 PR，用 `origin pr merge <pr>` 或 `gh pr merge <pr> --squash`。在 Origin 上，这条朴素命令还会合并你指定那个 PR 下方的所有 PR；在 GitHub 上，若某个 PR 的基分支仍是其父分支，它会合并进那条分支而不是主干。要回读 PR 以确认结果（`origin pr view <pr>` 或 `gh pr view <pr> --json state,mergedAt,baseRefName`），因为合并命令可能在合并队列只是把 PR 排入队列时就报告成功，而请求的自动合并也不等于已经合并。已落地的 PR 应显示为已合并、基分支为主干，而不是其父分支。只有当某个 PR 的判定覆盖其当前头提交时，才给它装上 `--auto`（Origin 的 merge-when-ready 或 GitHub 的 auto-merge），因为它会落地任何就绪的头提交。一次合并落地后，把基分支原为那条被合并分支的 PR 重定向到主干（`origin pr edit <pr> --base <trunk>` 或 `gh pr edit <pr> --base <trunk>`），把它的补丁移到合并结果之上，并用 `--force-with-lease` 推送。判定覆盖的是补丁而非其提交，因此第 3 步的 patch-id 规则决定该判定是否继续有效。等它的检查通过且判定仍然有效后，再合并它。
5. **它落地期间不要碰这个栈。** 第 4 步挪动下一个 PR 是对分支或基分支的唯一改动，因为一次合并落地的是它那一刻分支与基分支上的内容，无论有没有判定。在 GitHub 上，用 `/loop` 下的 `scripts/watch-pr/watch-pr --queued-stack` 盯住这一轮，直到它在天花板处报告 `COMPLETE`。把本轮的 PR 编号自下而上放进 `--stack-prs`，每次重启监视器时都传同一份列表。在 Origin 上，每次 `origin pr checks <pr> --watch` 返回后，都用 `origin pr view <pr> --checks` 重读当前 PR，直到天花板显示为已合并。当父 PR 合并后某个基分支转到主干上，这是预期行为，不是需要修复的损伤。如果合并卡住了，先弄清原因，再去改动任何东西。
6. **在天花板处停止。** 延展这段栈需要新的判定，所以那是重新走一遍第 1 步。

**回复：** 已验证的这段栈及其天花板，每个 PR 的判定及由谁给出，落地了什么、你如何确认，以及下一个缺口需要什么。
