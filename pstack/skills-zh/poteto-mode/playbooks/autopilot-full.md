### 全自动驾驶（Autopilot-full）

**你负责裁决，永远不负责 PR。每个 PR 由一名负责人从构建带到合并，而在你的集群（它从未写过这些代码）证明将要落地的代码之前，任何东西都不合并。**

一份裁决只覆盖一个补丁，一次全绿的 CI 只覆盖一个 head。第 4 步完整跑一次集群，只有重大改动才再跑一次。`playbooks/shipping.md` 里的 patch-id 规则可以沿用某条泳道的结果，而每个新的 head 都需要自己的全绿 CI。

1. **操作者的闸门优先。** 授权只覆盖队列里的条目，所以操作者声明归他的条目以及队列之外的 PR 一律停在合并就绪。要求你说明计划不等于放行。
2. **每个 PR 派生一名负责人，并把它的工作放在替补能找回的地方。** 整个项目只解析一次托管平台。默认用 GitHub CLI（`gh`）。如果 `command -v origin` 成功且 Origin 能解析该仓库，则所有 PR 操作都用 `origin pr`。否则留在 `gh` 上并记录这次退让。绝不要求 Graphite（`gt`）。每位负责人是一个 Cursor 云端智能体，它负责构建、按 `playbooks/opening-a-pr.md` 开 PR、在真实产物上验证改动、按 `playbooks/babysit.md` 盯守到全绿，并在第 4、5 步通过后合并。当该手册要求上报需要 rebase 时，负责人自己 rebase 自己的分支，并用 `git push --force-with-lease` 发布。

   尽早开 PR，让 CI 和机器人与工作并行。只有经过去水化（`cursor-team-kit` 插件提供的 `deslop` skill（`/deslop`））和 `/no-comments` 这一遍之后，代码才算就绪，因此完整集群跑在已完成的代码上。然后 rebase 到当前主干，并在自证之前上报代码就绪的 head，好让验证跑在补丁将要落地的基线上。之后每个 head 都要上报，自证、CI 与盯守都完成后上报合并就绪。修复轮次留在该基线上，除非主干冲突、导致 CI 失败，或已知有并发改动落到同样的文件，因为每次 rebase 都会重启 CI。在代码就绪那次推送之前，以及之后任何需要验证器的推送之前，对已提交的 head 运行仓库针对所涉路径的检查。

   假设 VM 会死掉。启动后不久就按 **show-me-your-work** skill 推送并在根智能体的存储里（路径见系统提示）开始一份决策轨迹，之后每完成一个单元就先推送再开始下一个。派生某个子代理的人要把它的 id、状态，以及从同类历史运行中得出的卡住判定时长记录到该存储，这样父级死掉时根智能体还能探查它。只对自己的分支强制推送，`--force-with-lease` 要钉在你最后一次推送或接管的 SHA 上；对于任何不是你做的推送，停下来上报给根智能体。
3. **负责人在主干上并行运行，绝不堆叠，** 这样每个 PR 各自独立落地。
4. **集群验证一次。** 完整集群在代码就绪的 head 上跑一次。只有当出现新行为、重新设计或大量新差异时才再跑一次完整集群。rebase、解决合并冲突或小修复只在新 head 上派一名验证者，纯文字改动则一个都不派。按 **swarm** skill 在代码就绪的 SHA 上铺开相互独立的验证者。它们重跑闸门，通过对应的控制 skill（例如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或指定的驱动器，在真实界面上实证承重行为，并审计差异。没有实机泳道，或在你审计合并就绪报告的回执之前，裁决不算干净，因为没有泳道会相信自己没核对过的说法。

   只为你拿得出证据的问题阻塞 PR：head 上有失败的运行，或 PR 把某行文档改错了。PR 的基线本来就有的问题（无论是主干，还是堆叠中位于它下面的那个 PR），除非 PR 复制了它或新触达了它，否则不构成阻塞。只有用户会踩到的 bug、失败的闸门，或交付文档写错才阻塞，其余一切都进后续事项。
5. **负责人只合并你验证过、并在其落地的主干上测过的内容。** 全绿的 CI 本身从不授权合并。集群各泳道一旦开始，合并准备就 rebase 到当前主干、上报新的 head，并等待 CI 全绿。

   合并前一刻拉取主干，并问它的改动是否可能影响该补丁，因为主干每动一次就 rebase 一次永远没有尽头。当将要落地的代码从未被测试过时——例如出现冲突、双方都改了同一个文件，或改变了该 PR 会跑哪些检查——就 rebase 并等 CI。如果冻结安装能在合并结果上通过，且该 PR 改动的包在那里解析出的结果与 head 上一致，那么双方都改过的锁文件不需要 rebase，因为那次安装测的就是将要落地的锁文件；安装失败则意味着必须靠 rebase 来修复它。当主干改动了补丁的调用方，或改动了补丁依赖的东西（例如它调用的代码或某个依赖版本）时，在合并结果上跑补丁的检查，通过就合并。其余情况直接合并。如果主干会迫使在合并准备之后再来第三次 rebase，就挂起并上报给根智能体，由它来编排相互冲突的工作。
6. **跑好根层。** 任何放宽闸门的做法——例如提高预算或加白名单条目——都需要验证者给出证明，再由你重新副签，因为负责人本身是想要全绿的那一方。在覆盖审批的授权下，该副签就是审批，负责人对它的记录会指向你的副签供泳道核对。被禁用或软失败的检查一定要摘掉，因为它已经不再守护任何情形。绝不给出来自托管平台的审批，也绝不绕过它，因为没有任何副签能覆盖它。

   操作者放行后，装上 `/loop 1h` 持续审计，直到没有委托的工作剩下，因为长跑会漂移，智能体会无声卡住。每个 tick 都从主干重读本手册并修正漂移，例如未上报的 head 或未登记的智能体，做法是让它的负责人补记，因为漂移是记录上的缺口，不是卡住。它要探查每个智能体，一直探到叶子泳道，并按各自的副作用判断，因为状态文字和摘要可能掩盖卡住的孩子。智能体报错、无法开始回合，或在超过卡住判定时长后毫无新动静，就算卡住；到第一个 tick 时既没推送也没写轨迹行的负责人同样算卡住。正在等你或等操作者的不算卡住，要回应它。卡住的智能体立刻替换，不必等它的停止落地。为操作者改变了什么的 tick 结束时按 **ketchup** skill 向他同步，什么都没改的 tick 保持安静。
7. **操作者叫停时立刻收手。** 暂停令以零写入命令下达到每位负责人。各自上报所处状态，并保留自己的任务简报直到操作者解除。

**回复：** 按 **ketchup** skill 向操作者同步，覆盖每个 PR 的状态与裁决、合并了什么、副签及其理由、未决的操作者闸门，以及挂起的后续事项，并附上每个 PR 与轨迹的链接。
