### 轨迹取证（Trace forensics）

**从产物出发做诊断，由你负责。**

这与 **运行时取证** 不同，后者是给活体进程加插桩。这里抓取已经存在。产物是固定数据集，读它，不要重跑。工具保持通用：用 DevTools 或轨迹解析器处理 cpuprofile 与 `.json.gz`，用文本编辑器处理 spindump，用你的堆工具处理 heapsnapshot。

1. 识别格式，用对的工具加载。在子代理里解析大产物（**guard-the-context-window** 原则 Skill），主线程只保留收敛后的结论。按 Subagents 章节所述，为每个子代理按任务选择推理档位。
2. 把原始产物转成可查询的形式。把轨迹或堆快照倒进 sqlite，每个样本、栈帧或节点一行。先到达可查询的形态，再开始读。
3. 收窄到原因。查询占时最多的那些栈帧，并沿调用树走到热路径。对泄漏，沿持有链从泄漏对象追到 GC 根。对 spindump，找出卡在 CPU 上或被阻塞的线程及其等待原因。
4. 归因到源码。借助产物自带的符号，把热帧映射到文件、符号与行号。没有源码映射的帧还称不上诊断。要么解析出符号，要么明说该产物不携带它们。
5. 如果你有配对的两次抓取，对比前后产物来确认。否则，把结论标为该产物所能支持的最强假设，而非已确认的原因。
6. 交回一份带引用的诊断，除非被要求否则不给修复。原因明确后路由到缺陷修复或性能问题。吞吐检查点保持一行：`throughput checkpoint: n/a, read-only forensics`。

**回复：** 产物与格式，收敛后的结论，源码位置，产物路径，以及是否有配对抓取加以确认。
