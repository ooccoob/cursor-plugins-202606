### 多阶段或多 PR 计划（Multi-phase or multi-PR plan）

**计划由你负责，代码不由你负责。计划是一份清单，负责人逐项打勾执行，操作者依据证据审计。** 计划本身就是交付物。不要动手实现。

1. 当改动只涉及一两个文件且做法明确时，跳过计划。说明这一点然后结束。
2. 写计划之前，用原型把悬而未决的问题定下来，见 `playbooks/prototype.md`。只有当某个产品或偏好上的取舍无法靠任何一次运行定夺时，才去问操作者。
3. 写出计划文件。开头写明要改什么、按落地顺序排列的 PR 编号，以及依赖图：哪些 PR 相互独立并从主干拉分支、谁等谁、每个 PR 可能触及哪些文件。然后每个 PR 一节。一个 PR 就是一处改动，带自己的证据（**sequence-verifiable-units** 原则 Skill）。每节都要有复选框，覆盖它依赖什么、它编辑哪些文件、它构建的那一处改动、你能看到的结果，以及它的验证。
4. 只有测试不足以构成验证。一个 PR 只有在它的单元、实机、性能三类复选框全部勾上时才算已验证。每个实机复选框都要用具体场景驱动真实界面，并给出通过谓词。性能复选框要写明指标、探针、先测出的主干基线，以及会判失败的那个数字。凡是改变交互的 PR，合并前要等操作者评审。
5. 交回计划路径然后停止。执行以操作者明确发话为起点。

**回复：** 计划路径，PR 编号及其依赖、以及需要评审把关的集合，还有哪些仍然未经证明。
