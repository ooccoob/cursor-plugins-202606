### 性能问题（Perf issue）

**测量的说法由你负责。做规划、做评审、核实数字。** 每个修复都要绑到一个测量上，不要用读源码代替测量。

1. 经由相应的控制 Skill 采集一份基线轨迹。用 **benchmark-checklist** Skill 审核基线，以及之后的每个数字。
2. 追查代码以落定假设。没实际跑过，就不要宣称某个性能上限。
   按顺序尝试性能口诀，从最便宜的试起：
   1. 别做它。与其把它做便宜，不如停掉那些结果无人使用的工作。
   2. 做它，但别重复做。
   3. 少做点。
   4. 晚点做。
   5. 趁人不注意时做。
   6. 并发地做。
   7. 用更便宜的方式做。

   当较早的一条口诀已经达到目标，就停止。
3. 依据轨迹规划修复。如果它跨越函数边界，先跑 `architect`。把实现委派给子代理，使用你配置的性能问题模型（默认 `claude-opus-5-5-xhigh-fast`）。按 Subagents 章节所述，为每个子代理按任务选择推理档位。评审 diff。采集修复后的轨迹。
   应用 **sequence-verifiable-units** 原则 Skill，在试下一次之前先验证每次尝试。
4. 解析并对比这些产物（JSON 转 sqlite，再做 diff）。“无定论”或搞错了界面都不算通过。要标记出来。
5. 在 PR 中引用这次测量。
6. 运行**开启 PR**。

若要做针对某指标的持续改进而非一次性修复，用爬山式迭代手册（`playbooks/hillclimb.md`）。

**回复：** 基线数字、修复后数字、增量、产物路径。
